# App Purpose
A native Android context-capture utility and AI agent pipeline designed to capture on-screen data and user inputs from anywhere in the OS and pipe them directly into a webhook (which will likely be processed by an AI agent at the other end).


# Core Architecture & Permissions
The engine relies on standard Android framework capabilities, avoiding root or ADB workarounds to maintain device stability.

AccessibilityService: Parses the semantic UI tree, extracts bounding boxes, and reads active text selections without needing manual clipboard actions.

MediaProjection: Captures raw pixel buffers. The standard system permission prompt will be accepted manually upon initialization.

NotificationListenerService: Hooks into the Android MediaSessionManager to passively extract active podcast metadata and exact playback timestamps.


## Floating Toolbar Overlay

# System-Wide Entry Points
Beyond the floating overlay, the capture engine integrates directly into the operating system for frictionless triggering.

Text Highlight Menu: Handled via ACTION_PROCESS_TEXT for extracting selections and enabling bidirectional, inline text replacements.

Share Sheet: ACTION_SEND intent filters catch and route shared URLs, text, and media files directly to the engine.

Both these entry points launch an input modal, displaying the tabs for switching between input types. The default input type is the same as whatever was last used. The context for these is the context provided by the text highlight or the share sheet.

# The engine
JSON packages are dynamically assembled by the background services right before sending an HTTP POST request to the configured webhook.

The payload is designed to be modular: fields are included or excluded based on the input method used and which context toggles are currently active.

## Ideas for payload structure
These are IDEAS for inspiration. They cover the sorts of things that might be considered to go in the payload. If there are more effective, better structured, or more useful fields then use those instead.

JSON Field	Data Type	Description
type	String	The trigger mechanism: "speech_to_text", "mic_audio", "clipboard_paste", "text_snippet", or "share_target".
timestamp	Long (Epoch ms)	Exact millisecond timestamp when the capture occurred.
source	String	Origin of the payload: "floating_overlay" or "system_share_sheet".
package_name	String	The Android package identifier of the active foreground application (e.g. com.android.chrome, com.google.android.youtube, com.twitter.android).
input_content (Optional)	String	The text content supplied by the user (spoken dictation, clipboard text, or custom text snippet).
active_context_sources	JSONObject	Booleans representing which context switches were active at capture time: screen_grab, app_tree, highlighted_text, and media.
media_context (Optional)	JSONObject	Rich metadata extracted when media or browser apps are detected. Includes platform, title, channel_or_artist, canonical url, timestamp, and playback_state.
highlighted_text (Optional)	String	Content from the currently focused or selected node (AccessibilityNodeInfo.FOCUS_INPUT or FOCUS_ACCESSIBILITY).
targeted_selection (Optional)	String	Bounding box coordinates if Point/Gesture selection mode was used.
app_tree_text (Optional)	String	Indented, hierarchical text tree extracted by traversing all AccessibilityNodeInfo nodes in the active window.
screenshot_base64 (Optional)	String	Base64-encoded JPEG image (compressed at 80% quality). If Point/Crop mode is active, only the cropped bounding box is encoded.

# Ideas for flow
Again this could be changed or improved
1. The user sends input from the input popup
2. The state of 4 context source toggles (screenGrab, appTree, highlightedText, media) and any Point selection is passed to the relevant services
3. CaptureAccessibilityService walks the active window's AccessibilityNodeInfo tree to pull text, media metadata, and focused elements. If screen_grab is enabled, takeScreenshot(...) extracts the hardware buffer, converts it to an ARGB bitmap, crops it (if Point mode is active), and compresses it to Base64.
4. The JSON object is constructed and logged
5. The JSOn is sent to the webhook. Response time and HTTP codes are logged in real time.
